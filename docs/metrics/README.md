# Логи прогонів і таблиці результатів ЛР3

Сюди складаються логи сценаріїв з docs/scenarios.md і таблиці, які я з них будую. Записи логічного аналізатора лежать окремо, у docs/captures/, але з тією самою назвою, щоб лог і VCD одного прогону легко було знайти разом.

## Структура

```
docs/metrics/
  README.md                       цей файл
  S1_2026-11-12_1030.log          лог прогону (пише tools/run_scenario.py)
  S3_2026-11-12_1105.log
  6.2.2_2026-11-12_1140.log
  ...
  results.md                      таблиці S1/S2/S3 і 6.2.x з умовами прогонів
docs/captures/
  S3_2026-11-12_1105.vcd          запис аналізатора того самого прогону
  6.2.2_2026-11-12_1140.vcd
```

## Як називати

- Лог: `<сценарій>_<дата>_<час>.log`. Назва сценарію - поле `name` з `tools/scenarios/<S>.yaml` (S1, S2, S3, 6.2.1 ... 6.2.7), дата і час - коли стартував скрипт на хості. Так файл називає сам `tools/run_scenario.py`, перейменовувати не треба. Якщо в ту саму хвилину такий файл уже є (перезапустив прогін), скрипт додає `_2`, `_3` і старий не перезаписує.
- VCD: Wokwi для VS Code після зупинки симуляції кладе запис у `wokwi.vcd` у корені проєкту (він у `.gitignore`). Я перейменовую його в ту саму назву, що й лог, тільки з `.vcd`, і переношу в docs/captures/. Якщо файл великий (довгий прогін), вирізаю потрібне вікно `tools/vcd_window.py`.
- Повтор того самого сценарію - це просто новий файл з іншим часом. Старі не видаляю, а в results.md пишу, який саме прогін узято в таблицю.

## Що записувати поруч з результатом

Методичка (6.3) просить, щоб у всіх прогонів були однакові умови і щоб їх було видно поруч з числами. Що з цього вже робить скрипт, а що треба дописати руками:

| Умова | Де видно |
|---|---|
| версія прошивки (git-хеш, `-dirty` якщо збирав з незакоміченими змінами) | перший рядок логу `# git=...`, рядки `BOOT` і `PERF` |
| варіант збірки (`PERF`, `TEST_I2C_FAULT`, `LAB2_CAP`) | перший рядок логу `build="..."` (з `firmware/build/build.cfg`), `perf=` у `BOOT` |
| ручки (`lcd_ms`, `lcd_chars`, `imu_ms`, `log`) | рядок `KNOBS` після `BOOT` і в кожному `stats` |
| що робилось руками і коли | рядки скрипта `# ! <підказка>` і `# > <команда>` у лозі; повтори загублених команд - `# > <команда> (повтор: CR + команда)` |
| середовище: Wokwi для VS Code (версія з docs/architecture.md), форма B | **дописати** в results.md |
| що всі часи - симуляційні | **позначати** «(сим.)» у кожній таблиці (методичка 2.2); `stats_table.py` робить це сам |
| канали аналізатора | docs/pinout.md і docs/captures/README.md; якщо щось перемикав (наприклад, D5 назад на PA15) - **дописати** |
| відхилення від сценарію (натиснув менше разів, симуляція ставала на паузу тощо) | **дописати** в results.md |

Час подій береться тільки з міток МК (`<мс>` на початку рядка і `t_us` у `EVT`), а не з часу, коли рядок прийшов на хост (методичка 5.2). Скрипт свого часу в рядки не додає.

## Як отримати таблиці

```
python3 tools/stats_table.py --s1 docs/metrics/S1_<…>.log --s2 docs/metrics/S2_<…>.log \
        --s3 docs/metrics/S3_<…>.log --vcd S3=docs/captures/S3_<…>.vcd     # таблиця у форматі 6.3
python3 tools/stats_table.py --blocks docs/metrics/6.2.5_<…>.log            # точка зламу, по блоках
python3 tools/evt_latency.py --md docs/metrics/6.2.2_<…>.log                # затримки за EVT, p99
python3 tools/vcd_timing.py --md --label 6.2.2 docs/captures/6.2.2_<…>.vcd # те саме з аналізатора
```

Вивід - markdown, його я вставляю в results.md разом з рядком «Умови прогонів», який друкує `stats_table.py`.
